# ADR 004 — Excel administrativo sobre cPanel PHP 8.3

Decisión: OpenSpout 4.32.0, lectura XLSX en streaming y escritura de una plantilla sin datos comerciales. Se fijó la versión en composer.lock, manteniendo platform.php 8.3.0. OpenSpout 5 requiere PHP 8.4+, incompatible con la versión del hosting informada por el dueño. No se usa WordPress ni un importador del catálogo anterior.

La descarga dist de GitHub API recibió HTTP 403; Composer instaló mediante su ruta de Git HTTPS soportada, con la fuente oficial y commit `41f045c1f632e1474e15d4c7bc3abcb4a153563d` registrado en el lock. No se desactivaron TLS ni verificaciones. composer audit no reportó vulnerabilidades ni paquetes abandonados.

Preflight limita ZIP/partes/XML/dimensiones y rechaza contenido activo antes de usar el lector. Las filas se validan en servidor; preview no modifica catálogo. El payload normalizado se cifra en storage privado. Se reutilizan import_batches/import_errors ya presentes, sin migraciones nuevas ni cambios en datos iniciales.

La confirmación usa un lock de proceso finito y transacción con bloqueo de filas/fingerprint del catálogo. El batch completado hace los reintentos idempotentes. Reemplazo es retirada reversible de ausentes, con snapshots de ventas intactos. Se crea copia cifrada usando el servicio de backups existente antes de escribir; restaura completa solo en staging según la política actual.

Actualización posterior: Imagen admite fotos internas OOXML y Excel 365, sin descargas externas. ImageUpload comparte la decodificación/reprocesado existente, con límites y preparación finita cifrada. La aprobación/publicación exige casillas explícitas y permisos de servidor; no es automática. EXCEL_CON_FOTOGRAFIAS.md describe el flujo. La importación procede exclusivamente de archivos nuevos elegidos por el administrador; no se crea ninguna tarea que lea las fuentes históricas ni se añaden datos a las semillas.

Requisitos adicionales: DOM, XMLReader y ZIP habilitados en PHP. Dependencia y autoload de producción incluidos en la entrega, sin instalación de Composer en cPanel. Límites de memoria y upload del hosting deben permitir el archivo; para archivos con fotos se recomienda memory_limit 256M, upload_max_filesize 128M y post_max_size 144M, sujetos al plan real y al límite efectivo mostrado por el panel.

Compatibilidad de ajustes de impresión: el rechazo indiscriminado de .bin impedía importar libros estándar con printerSettings. Solo se exceptúan xl/printerSettings/printerSettingsN.bin (N positivo), de hasta 256 KB, cuyo tipo declarado sea application/vnd.openxmlformats-officedocument.spreadsheetml.printerSettings. Se ignoran completamente sus bytes, sin extracción ni ejecución. El resto de binarios sigue denegado; no se relajan tamaños globales, macros, objetos, relaciones externas, entidades ni validación/reprocesado de fotos. Los rechazos de tamaño y contenido ahora tienen avisos separados, para diagnosticar la instalación sin atribuir contenido malicioso al archivo original no inspeccionado.

Preparación simultánea: se eliminó el flock no bloqueante por lote que devolvía 409. El bloqueo de fila InnoDB dentro de la transacción ya serializa estado e índice de fotos y permite esperar un grupo finito sin depender del filesystem compartido. Se comprobó con dos procesos PHP/MariaDB reales y con un timeout InnoDB. Solo los códigos MySQL 1205/1213 devuelven reintento; otros QueryException no se ocultan. Un POST tardío sobre un estado distinto de processing es no-op después de autorizar usuario/medio. La confirmación mantiene su bloqueo propio, fingerprint, backup y transacción; no se procesa catálogo desde prepare. El cliente cancela su temporizador en el primer submit y al cancelar el lote.
